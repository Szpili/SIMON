# Pre-registration — M3 false-positive rate under honest operator variability

**Written before measuring, so the threshold cannot be tuned to the data afterwards.**
(Commit this file before running the matrix. Any change is a new, dated revision below.)

## Question

Does the M3 policy we actually ship flag an **honest** node that differs from the reference
only in ways an honest operator legitimately varies (device, backend, build, batching, KV-cache
quantization, offload split, parallel load, vendor)?

## Metric (the one the code uses)

- **`contain2`** per step: the node's chosen token is in the reference's top-2 **within
  `max_margin`**. This is what `simon_core::m3::ocena` computes — **not** `top2_overlap`
  (Jaccard), which no decision path uses.
- Per prompt: `suspicious_fraction = 1 - contain2_fraction` over N steps.
- **Flagged** iff `suspicious_fraction > max_poza` (shipped: `max_poza = 0.02`,
  `k = 2`, `max_margin = 0.25`).

## Unit of evidence

- **One distinct prompt text.** Not one token, not one repeated prompt.
- **≥30 different prompts**, written by people (not generated by the models under test).
  Repetition of a prompt does not add independent units; it is reported, not counted.

## Procedure

For each honest configuration `C` and each prompt `p`:

1. Node = `C` generates N greedy tokens (its **own** trajectory).
2. Reference (config #1) teacher-forces the node's sequence and records per-step top-k.
3. Compute `suspicious_fraction`; flag iff `> max_poza`.

The reference is **not** scored against itself as evidence (that arm is a sanity check only).
Sequences are hashed (`seq_hash`) into every row so a shifting reference cannot hide.

## Pass / fail criterion (fixed in advance)

- **PASS:** no honest configuration has **any** prompt flagged.
  At 0/32 the 95% upper bound on the per-prompt false-positive rate is **≈ 9%** (Clopper–Pearson).
- **FAIL:** any honest configuration flags any prompt.
  Then **M3 stays telemetry only** — it does not trigger escalation. Slashing is already off
  (`m3::decyzja` cannot emit `HardFail`). The receipt layer is unaffected and remains the product.

No AUROC will be published until this matrix is complete. No new M3 features will be added
until it is complete.

## Configuration matrix (one per class; `ref` = config 1)

| # | Configuration | What it tests |
|---|---|---|
| 1 | CUDA, KV f16, default `-b` | reference |
| 2 | CPU only | different backend |
| 3 | different `-b` / `-ub` | batching |
| 4 | KV `q8_0` | cache quantization |
| 5 | KV `q4_0` | aggressive cache quantization |
| 6 | partial `-ngl` | offload split |
| 7 | flash-attn on/off | different kernel |
| 8 | older llama.cpp commit | build drift |
| 9 | `-np 4` under parallel load | real server batching |
| 10 | Vulkan on the 3090 | same hardware, different stack |
| 11 | **ROCm/HIP on the MI300X (AMD)** | **different vendor** |

## Scaling (step by step)

1. **Sanity:** one config, one prompt, checked by hand — `seq_hash` matches, the reference
   regime matches, the numbers are right.
2. **10–12 configs**, one per class above, ≥30 distinct prompts.

## Notes / honesty

- The prompt set must be **human-written**; if any are machine-written, say so and treat the
  run as provisional.
- The AMD arm is a **different vendor** and also satisfies the hackathon's AMD requirement;
  it is one configuration here, not a separate project.
- If a config's model cannot run (e.g. no `sm_52` kernel), record it as unavailable, do not
  substitute silently.
- **Either result is publishable:** "our own critic refuted our first result; we then measured
  false positives under honest variability, including AMD vs NVIDIA" is a strong, honest story.
