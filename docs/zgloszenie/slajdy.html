THE PROBLEM

A signature proves who wrote the number.
It never proves the number is true.

Every decentralised inference network hands you a signed claim and calls it a proof. Ours started out doing the same. The interesting engineering is in the gap between those two words.

This is the thesis. Say it once, slowly. The rest of the deck is what follows when you take it seriously — including the two places where we caught ourselves getting it wrong.

What a receipt proves — and what it does not

Proved today

A registered node signed this exact answer as the result of this job.

  • Ed25519 signature over a commitment to the output text
  • Bound to the job id — a valid receipt from another run cannot be reused

Not proved

That the declared model generated it.

  • A malicious node can sign arbitrary text with a correct digest
  • Token counts and timings are signed declarations, not independent measurements

Binding model + prompt + execution + output needs an execution audit. It is not implemented, and the repository says so.

The right-hand column is the one that matters. Most projects only ever show the left.

MEASURED, NOT PROJECTED

Verification is cheap enough to pay for

An audit is one forward pass. The job must also decode — and decoding is ~55× slower per token.

Lower bound: this is the forward pass alone, without activation extraction and hashing. Raw data is in the repository.

This number decides whether verification can come out of the job price. It can.

Heterogeneous on purpose — and it shows

Two GPUs, two serving stacks, two models, one network. The engine and model on each result come from the signed receipt, not from a label we wrote beside it.

RTX 3090 · vLLM 0.27.1

Qwen3.8-27B · full context admission gate

64.94 tok/s

RTX 3080 Ti · Ollama 0.34.0

Bielik 11B · admission gate disabled, and the node says so

6.50 tok/s

A node that cannot verify its own context budget declares that, instead of pretending to check.

Adding the second node immediately exposed two false statements in our own receipts: the node announced a model it was not serving, and every receipt claimed vLLM even when Ollama did the work. Both fixed the same day. Heterogeneity is not a feature list here — it is a test instrument. One node could never have surfaced those two bugs.

Does an honest AMD node compute the same thing as an honest NVIDIA one?

If the answer is no, naive fingerprint comparison slashes honest participants — and every cross-vendor network has this problem, noticed or not.

Three of our own claims, withdrawn in public

The receipt did not bind the answer

The digest covered metadata; the text travelled unsigned.

Found while checking whether we could count tokens at all

A constant pretending to be a measurement

Throughput was tokens / 65.0 — one card's figure, applied to every node.

Survived the code, a comment claiming "hard measurement", and a demo showing one number on two GPUs

A check the whitepaper promised and we never wrote

Both papers said the client checks a receipt is single-use. It did not.

Corrected in both languages; the ledger now gives it somewhere to be true

Each entry in docs/SECURITY-LOG.md describes the previous behaviour, not only the fix, so a reader can judge what older receipts actually proved. Any project can show what works. This slide is the reason to believe the rest of the deck.

A fingerprint mismatch triggers re-audit, not punishment: we will not ship a threshold we cannot defend. The ledger records work, never a balance, because verified work is not the same as independent demand. Colour is doubled by the words here, so the table still reads without it.

Idle capacity, turned into burst capacity — with a receipt you can check

Not "earn while you sleep": at 350 W a night of full load is worth less in commodity tokens than the electricity. The value is work that must not leave your machines, results that can be checked, and five GPUs at once on the morning you need them.
